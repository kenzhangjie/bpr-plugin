# 翻译三步法 · Translate → Reflect → Improve

> 📌 **本文件是 BPR 内部副本,服务于 /bpr 流水线**。
> 如果你**不在** /bpr 流程中,而是想单独翻译一段英文 → 可使用独立的 `translate` skill(若已安装,触发词:翻译这段 / 帮我翻 / translate this 等)。
> 两边方法论保持同步。改一边请同步另一边。

## 为什么用三步法

一次性翻译的瓶颈不是模型"不会",是**没有被引导去自查**。
长句容易漏、风格容易飘、翻译腔容易留下、术语容易前后不一致。
Andrew Ng 的开源 [translation-agent](https://github.com/andrewyng/translation-agent) 验证过:
插入一个 reflection 步骤,质量能显著上一个台阶。

BPR 场景适配:**每章一次三步**(单章 30-100 句,context 还能装得下),
不要每句一次三步(冗余且慢)。

---

## 🤖 给 Claude 的执行指令(/bpr 触发时按这个走)

每翻一章正文,**内部**按下面三步推进。
**最终只输出 Step 3 的结果**,Step 1 / Step 2 是模型自检过程,不显示给用户。

### Step 1 · Draft 直译

一句一句翻,先求"意思对、不漏"。**允许翻译腔**,这一步不润色。

保留:
- 专有名词、产品名、人名、品牌、公司名(原文不译)
- 已建立的英文术语:PM / IC / PMF / CAC / LTV / ARR / agent / harness /
  agentic / RAG / leverage / specific knowledge / agency / playbook / flow 等
- 数字、单位、$ 符号(不换算)
- inline link `<a href="...">...</a>`(原样保留;中文段重复同一个 link)

### Step 2 · Reflect 反思

对比原文 vs Step 1 译文,从 4 个维度**逐句内部检查**:

1. **Accuracy 准确性**
   - 漏译(整句 / 整子句 / 修饰语漏掉)
   - 加译(原文没有但译者塞进来的)
   - 误译(意思偏了)
   - 数字 / 单位 / 时间错位

2. **Fluency 流畅性** — 警惕这些翻译腔结构:
   - "X 是被 Y 所..." → "Y 做了 X"
   - "这是非常 X 的事情" → "这件事很 X"
   - "对于 X 来说,Y 是..." → "X 需要 Y"
   - "在 X 的情况下" → "X 时"
   - "X 这种东西" → 直接说 X
   - "我们应该考虑这个事实,即..." → "我们应该想想:..."
   - 长串"的"字定语(超过 3 个"的"在一句里 = 烂翻译信号)
   - **英语习语字面照搬 = 翻车信号**:看到任何习语 / 比喻先在中文里找对应成语,**不要逐字翻**:
     - "world of difference" / "world of incrementality" → ❌ "天和地的差别" → ✅ **天壤之别**
     - "night and day" → ❌ "黑夜和白天" → ✅ **天差地别**
     - "moving the needle" → ❌ "移动指针" → ✅ **撬动结果**
     - "low-hanging fruit" → ❌ "挂得低的果子" → ✅ **唾手可得的** / **easy win**
     - "boil the ocean" → ❌ "把海煮沸" → ✅ **想一口吃成胖子**
     - "skin in the game" → ❌ "皮肤在游戏里" → ✅ **真金白银下场**
   - **行业术语降级到口语 = 翻车信号**:SaaS / 产品 / 商业类内容必须用行业标准译法:
     - monetization → ❌ "收钱" / "赚钱" → ✅ **商业化**
     - engagement → ❌ "互动" → ✅ **参与度**
     - retention → ❌ "留住用户" → ✅ **留存**
     - churn → ❌ "跑掉" / "走人" → ✅ **流失**
     - traction → ❌ "火了" → ✅ **增长势头** / **起势**
     - moat → ❌ "壁垒" → ✅ **护城河**
     - flow state → ❌ "状态好" → ✅ **心流**
     - incrementality → ❌ "多赚" → ✅ **增量** / **增量贡献**
     - ad-hoc purchase → ❌ "临时买" → ✅ **按需购买**

3. **Style 风格** — 是否抓住作者语气?
   作者语气速查表:

   | 作者 | 关键词 | 译文应避免 |
   |---|---|---|
   | **Naval Ravikant** | 直接 / 反共识 / 口语 / 偶尔挑衅 | 学术腔、长定语、过度修饰 |
   | **Paul Graham** | 安静 / 精确 / 不修饰 / 短句多 | 感叹号、强调副词、口语化插入语 |
   | **Andrej Karpathy** | 工程师式幽默 / 实用主义 / 自嘲 | 过度严肃、装权威、华丽辞藻 |
   | **Lenny Rachitsky** | 友好访谈式 / 提问驱动 | 学究气、机械结构 |
   | **Anthropic / DeepMind 官方博客** | 干 / 密 / 谨慎 / 不夸张 | 营销腔、感叹号、夸张副词 |
   | **Schopenhauer / Emerson 类经典** | 庄重但有刀锋 / 长句但不拖沓 | 网络口语、emoji 化表达 |

4. **Terminology 术语**
   - 同一概念前后翻译是否一致(如 agency 一会儿"主动权"一会儿"agency"——挑一种坚持)
   - 保留英文的术语是否**真的**需要保留,还是可以用更准的中文
     - 经验法则:**业内通用 + 中文没有对应词** = 保留英文(MCP / harness / agent)
     - 业内通用 + 中文有标准译法 = 用中文(prompt → "提示词" 也可以保留;leverage → 杠杆)
     - **混用不可以**:同一篇里 agency 既翻成"能动性"又翻成"agency",必须改齐

### Step 3 · Improve 改写

基于 Step 2 的内部反思重写。

**约束:**
- 句级对照不变(原文一句 → 译文一句,不合并、不拆分;
  长复合句允许在分号 / 连接词处拆 2 句对照,但要在 Step 1 已经拆了)
- 中文读起来像中文,不像翻译过来
- 风格匹配作者(参照速查表)
- Step 1 的术语 / link / 专有名词原则继续保持
- inline link 必须在 EN 和 ZH 段都保留

最终输出格式:沿用 BPR 标准的 `<div class="bilingual">` + `<p class="en">` + `<p class="zh">` 结构。

## 📋 作为独立 prompt 用(在外部 LLM 里)

如果用户想在 ChatGPT / Gemini / 其他 LLM 上单独用这套方法,
把下面这段整个复制过去 + 在末尾粘贴英文原文:

```text
你是一名顶级英译中译者,服务对象是中文母语 + 懂英文术语的科技 / 商业读者。
请按下面三个步骤完成,每一步必须输出。

【Step 1 · 直译草稿】
忠实翻译,不漏一句,不润色。
保留原则:
- 专有名词、产品名、人名、品牌、公司名:保留英文原文
- 行业通用术语(PMF / agency / leverage / specific knowledge / harness /
  agent 等):保留英文
- 数字、单位、$ 符号:不换算
- inline link 原样保留

【Step 2 · 自我反思】
对比原文和 Step 1 的译文,从下面 4 个维度逐条挑问题
(每条要指明"原文 X 处 → 译文 Y 处 → 问题是什么"):
1. Accuracy 准确性 — 漏译、加译、误译、数字错位
2. Fluency 流畅性 — 中文是否通顺,有没有翻译腔
   (被动语态、长定语、of 结构、"X 这种东西"、"对于 X 来说")
3. Style 风格 — 是否抓住了作者的语气
   (在这里说明作者是谁:例 "Naval = 直接 / 反共识 / 口语;
    PG = 安静 / 精确 / 不修饰")
4. Terminology 术语 — 同一概念前后翻译是否一致

至少给 5 条。如果没问题,写"无明显问题",但一定要做这一步,不能跳。

【Step 3 · 改进版】
基于 Step 2 的反思,重写译文。
要求:
- 句级对照不变(原文一句 → 译文一句,不合并、不拆分)
- 中文读起来像中文,不像翻译过来
- 保留 Step 1 的术语 / link / 专有名词原则
- 风格匹配作者

只输出最终中文译文,不要任何解释。

──────────────────
【作者语气说明】
<在这里写一句:作者是 X,语气特征是 Y / Z / W>

【待翻译原文】
<在这里粘贴英文>
```

## 🔥 极致版:三轮独立调用

最高质量做法(Andrew Ng 原始 agent 的做法):

1. **第 1 次调用** —— 只给 Step 1 prompt,模型只产出直译草稿
2. **第 2 次调用** —— 给 Step 2 prompt + 原文 + Step 1 草稿,模型只产出反思列表
3. **第 3 次调用** —— 给 Step 3 prompt + 原文 + Step 1 草稿 + Step 2 反思,模型产出改进版

好处:Step 2 不会被自己的草稿"锚定"——它在新 context 里看到自己的产出,
心理距离更远,挑出的问题更狠。

代价:3 倍 token,3 倍延迟。
对 BPR 这种 8000 字 podcast,**只对最关键的章节用**(例如 TL;DR 选出的金句段落)。
其他章节用单 prompt 三步法,质量约 80-90%,够用。

## 反例对照表 · 翻译腔常见结构

| ❌ 翻译腔 | ✅ 自然中文 |
|---|---|
| "他被认为是一个伟大的工程师" | "大家都觉得他是个厉害的工程师" / "他被公认是个伟大的工程师" |
| "这是非常重要的事情" | "这件事很重要" |
| "对于初创公司来说,X 是必要的" | "初创公司需要 X" / "做初创离不开 X" |
| "在大多数情况下" | "多数时候" / "一般来说" |
| "这种类型的产品" | "这类产品" / 直接说产品名 |
| "我们应该考虑这个事实,即 X" | "我们应该想想:X" / "别忘了 X" |
| "X,它是 Y" | "X 是 Y" |
| "通过这种方式" | "这样" / "这么做" |
| "做出贡献" | "贡献" / 视语境用具体动词 |
| "在...的过程中" | "...的时候" / "...时" |
| "拥有一个 X" | "有一个 X" / 直接说"有 X" |

## 自检快速 checklist

翻译完一段后扫一眼:
- [ ] 一句英文 = 一句中文(没合并、没拆分)
- [ ] inline link 在两段都在
- [ ] 同一术语前后翻法一致
- [ ] 全段没有超过 3 个连续"的"字定语
- [ ] 没有"被...所..."句式(除非真的需要被动)
- [ ] 没有"X 这种东西"的填充表达
- [ ] 数字 / 单位 / 链接全对
- [ ] 大声读一遍中文,听起来像中文,不像翻译软件的输出
